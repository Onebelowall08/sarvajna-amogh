| WINDOW_30000ms | 30000 | 30000 | 552 | 552 | 1.000 | 25.710 | 0.000 | 0.000 |

Execution recall is unaffected by window width. What the window governs is spurious pairing: a wider window keeps more concurrent requests indexed under the same key, so the join pairs a kernel event with a record from a different request more often.


Across the coupled cells the object path records 8.27 to 26.45 per cent, the destination endpoint no cross-request pairs at any width, and the declared identifier no cross-request pairs at any width.

The object path is the only key on which the benign and attack populations contend. Benign authorised reads draw from the same pool of 512 objects the authorisation failures target, and a permitted read is not indexed as a correlation candidate, so each one leaves two kernel file opens with no application record of their own. Those are what an authorisation denial can be paired with by mistake, and the window decides how long they remain available. Benign outbound fetches go to a different host altogether, so the destination predicate has no such population and records none even though one probe in sixteen shares a port with another. The declared identifier records none because a unique key holds exactly one candidate, which is by definition the right one.

The rise saturates rather than continuing, and the point at which it does is predicted by the workload. Benign authorised reads cycle the 512-object pool monotonically at roughly 35 per second, so a full sweep takes about 15 seconds. Below that, widening the window admits more of the pool and mispairing rises; at and beyond it the whole pool is already covered and the 20 and 30 second cells sit together at the top of the range.

The ceiling is well short of every pairing being wrong, because the index is scanned newest first and both sides of a request are collected within three milliseconds of each other, so the denial's own kernel event is usually the most recent candidate on that path. Mispairing occurs in the minority of cases where a benign read landed on the same object in between.


The decoupled cell separates the two parameters. It holds the buffer horizon at 60 seconds while narrowing the window to 2, and records 3.80 per cent spurious pairing, the lowest of any configuration and below the narrowest coupled cell at 8.27 per cent. Had the horizon driven the effect, that cell would sit with the widest windows rather than below the narrowest. The window governs how long an object stays indexed and therefore how many concurrent requests can be paired against it; the horizon governs only how long an unmatched kernel event waits before being reported unexplained.


A cross-request pair is identified by a gap of more than 100 ms between the application's timestamp and the kernel's. That proxy separates cleanly for the resource-identity predicates, where a mispairing lands on whatever request last touched the same object. It does not separate for proximity matching, where an unrelated record is usually within 100 ms at this request rate, so the proximity baseline's misattribution is established by its false positives and by the collateral damage in T5 instead.

## T5  Automated response, and what it cost

| Cell | Predicate | Attacks | Attributed | Attribution recall | Primary-class recall | Revocations | Principals revoked | Requests | Refused | Refused % | Legitimate refused | Attacks refused | Misattributed |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

| ENFORCE_TemporalBaseline | temporal | 1655 | 1101 | 0.665 | 0.665 | 1221 | 1221 | 5343 | 3519 | 65.860 | 3519 | 0 | 0 |
| ENFORCE_Baseline | deterministic | 1635 | 1635 | 1.000 | 1.000 | 1635 | 1635 | 5264 | 0 | 0.000 | 0 | 0 | 0 |

Across the three cells the user-scoped tier revoked 4,122 principals and refused 4,721 requests, of which 4,721 were legitimate and 0 were attacks.


Not one refused request was an attack. This follows from the adversary the workload models: an attacker who draws a fresh principal for each attempt never encounters the revocation issued against the previous one. Principal-scoped response therefore prevents nothing against a rotating adversary while retaining its full cost against a stationary legitimate population. It is effective where the principal persists, which is the case for a compromised account but not for the attacker modelled here. The pod-scoped tier does not share this property, because it acts on the workload rather than on the identity.


The deterministic baseline refuses nothing at all. It wrote one revocation per attributed attack and no later request was refused, which is what follows when the revoked principals do not transact again. The proximity baseline refuses a majority of all traffic, because the principals it revoked were legitimate users who do.


One second-order effect is worth stating explicitly. The proximity baseline's measured false-positive count is far lower under enforcement than in the ablation, because the principals it wrongly revoked are refused before they can issue the requests that would have been counted against it. Its apparent precision improves because it denied service to the evidence, and the enforced figure should not be compared with the unenforced one.


Attribution recall is not comparable between these rows: the forgery cell issues stripped and forged attempts that the others do not, so its denominator contains attacks no configuration could attribute. Primary-class recall is comparable, and reads 1.000 in both deterministic cells. Enforcement does not degrade attribution; the attack mix differs.


## T6  Latency decomposition, milliseconds

| Class | n | Spawn p50 | Export p50 | Transport p50 | Correlate p50 | Act p50 | Pipeline p50 | Pipeline p95 | Pipeline p99 | End to end p50 |
|---|---|---|---|---|---|---|---|---|---|---|
| BOLA_AUTHORIZATION_BYPASS | 543 | 0 | 3 | 0 | 3 | 0 | 3 | 7162 | 8502 | 6 |
| RCE_COMMAND_INJECTION | 526 | 2 | 496 | 1 | 5 | 0 | 6 | 10 | 14 | 504 |
| SSRF_UNAUTHORIZED_PROBE | 570 | 0 | 3 | 0 | 1 | 0 | 2 | 9 | 186 | 6 |

Three components with three owners. Spawn is the application's: the interval between writing its own record and the kernel observing the process it started, and it exists only for the execution class. Export is the kernel observability layer's. Transport, correlation and action are this work's, and their sum is the pipeline column.


The execution class carries a kernel export cost the others do not, and the pod-quarantine cell measures both populations at once: its in-pod probe generates unlabelled executions alongside the labelled ones, under the same exporter in the same seconds. Across all 1,951 executions in that cell, most of them unlabelled, the median export delay is 24 ms. Across the 74 that carry a request identifier it is 494 ms. The difference is the cost of capturing the process environment, which is the mechanism the declared identifier depends on. It is a property of the observability layer rather than of the correlator, and it bounds the fastest achievable response for that class.


The object-access class carries a tail the others do not: a p95 of 7.2 seconds against a 3 ms median. A read produces two kernel file opens, and the second has no application record of its own, so it waits in the buffer until the correlation window closes. The tail is therefore bounded by the window, and is the same mechanism that produces the spurious pairing in T3 seen from the latency side rather than the correctness side. It affects when an unexplained event is reported, not whether an attack is attributed: recall on that class is 1.000.

Egress severed is the figure to quote. It is measured by a probe running inside the pod at 0.1 second resolution, polling from the moment the response action was taken. The endpoint-enforced column is an upper bound only: its poll begins after the cell's fixed wait, so it reports when the measurement looked rather than when the datapath converged, and both collections of this cell returned the same value to within a thousandth of a second for that reason.


This is one observation. The environment verification performed before each collection applies the same label and polls from the instant it is applied; across 5 such checks still traceable to a surviving file, convergence ranged from 16.3 to 30.6 seconds. Four are recorded in new_suite_console.log and one in verification_20261005_121118.json, both archived with this suite. Earlier sessions produced further observations that are not quoted, because the verification report is overwritten on each invocation and those runs were not captured to a log. The range is cited as context for the single measured value, not as a distribution derived from the suite.


Containment is two to three orders of magnitude slower than the response action that triggers it. The action itself completes in milliseconds; the network datapath converges tens of seconds later, and that interval belongs to the network plugin rather than to this work.

| Cell | Principals revoked | Transacted again | Ever refused | Effect lower bound p50 (ms) | Effect upper bound p50 (ms) | Effect upper bound p95 (ms) |
|---|---|---|---|---|---|---|
| ENFORCE_Baseline | 1635 | 0 | 0 |  |  |  |
| ENFORCE_Forgery | 1266 | 20 | 20 | 0 | 611 | 1745 |
| ENFORCE_TemporalBaseline | 1221 | 120 | 120 | 0 | 918 | 3132 |

The revocation takes effect at some moment between the last request the principal still had served and the first that was refused. Both bounds are reported, because the interval between them is the principal's own request interval and not a property of the pipeline. Neither is comparable with the pod-scoped containment figure in T7 without that caveat: containment is polled continuously, this is observed only when the principal next transacts.


The column that matters most is the second. A revocation issued against a principal who never returns has no observable effect at all, and the gap between principals revoked and principals that transacted again is the direct measurement of that. It is the reason the deterministic baseline refuses nothing while revoking more principals than either other cell.


The request that triggered each revocation is excluded from the count of requests after the action. It was answered before the action was taken, but the workload generator writes its ground-truth row only once the response has returned, so for a small fraction of attacks that row carries a timestamp later than the action it provoked. Counting it would report a principal that never returned as having transacted again and escaped enforcement.

## Validity

- 19 cells, each verified by the collection harness against its own gates before the suite continued. A cell that failed stopped the suite; its rows were deleted and verified gone before it was collected again, so no cell appears twice in the data

- Reason codes partition every cell's events exactly: no event was reported twice, left held, or placed in no category. Checked by the harness per cell and recorded in the suite ledger

- No detection carries an attack issued by another cell, and none carries an identifier absent from ground truth. Same source

- The structural claim that proximity and resource-identity matching cannot bind a process execution is re-checked here against the archived rows, independently of the collection logs, and holds in every cell

- Every request reached the application. Requests refused by an enforced revocation are counted as delivered, because they were answered by it; counting only HTTP 200 would score every successful enforcement action as a delivery failure

- The correlator never fell behind: its queue was sampled throughout each cell and peaked far below the level at which a cell's latency would describe the queue rather than the pipeline

- One repetition per cell. Intervals quantify sampling uncertainty within a cell, not reproducibility across collections, and no difference between cells is tested for significance
